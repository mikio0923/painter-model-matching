# 決済システム 要件定義書

> 作成日: 2026-04-16
> ステータス: ドラフト（レビュー待ち）

---

## 1. 概要

本サービス「Palette」における決済機能の要件を定義する。
画家がモデルに対して報酬を支払う仕組みを、安全かつ法的に適切な形で構築する。

---

## 2. ビジネス要件

### 2.1 決済の対象

| 取引種別 | 説明 |
|----------|------|
| 依頼報酬 | 画家がモデルへ支払う撮影・ポーズ等の報酬 |
| プラットフォーム手数料 | 取引成立時にPaletteが徴収する手数料 |
| 有料オプション（将来） | プロフィール上位表示、注目表示等の有料機能 |

### 2.2 決済フロー（推奨案）

```
1. 画家が依頼を作成（報酬額を設定）
2. モデルが応募
3. 画家が応募を承認
4. 画家が報酬を「仮払い」（エスクロー）
5. 撮影・作業が完了
6. 双方が「完了」を確認
7. モデルへ報酬が「確定払い」される
8. プラットフォーム手数料を差し引いた金額がモデルに振り込まれる
```

### 2.3 手数料モデル（要決定）

| 項目 | 選択肢 |
|------|--------|
| 手数料率 | 10% / 15% / 20%（要決定） |
| 負担者 | 画家側 / モデル側 / 折半（要決定） |
| 最低手数料 | 設定するか（要決定） |

## 3. 技術要件

### 3.1 決済ゲートウェイ選定

| サービス | メリット | デメリット | 推奨度 |
|----------|---------|----------|--------|
| **Stripe** | グローバル対応・エスクロー(Connect)対応・Laravel公式パッケージ(Cashier)あり | 本人確認(KYC)のハードルがやや高い | ★★★★★ |
| **PAY.JP** | 国内特化・日本語サポート・審査が比較的通りやすい | エスクロー機能なし・自前実装が必要 | ★★★☆☆ |
| **GMOペイメント** | 国内大手・銀行振込対応 | 初期費用・月額費用が高い・APIが複雑 | ★★☆☆☆ |

**推奨: Stripe Connect**
- エスクロー（仮払い→確定払い）をプラットフォーム側で管理できる
- Laravel Cashier + Stripe Connect で実装の親和性が高い
- モデル側の振込先口座登録もStripe側で完結

### 3.2 Stripe Connect アーキテクチャ

```
Palette（プラットフォーム）
    ├── Stripe Account (Platform)
    │
    ├── Connected Account: 画家A（支払い元）
    ├── Connected Account: 画家B
    │
    ├── Connected Account: モデルX（受取先）
    └── Connected Account: モデルY
```

### 3.4 実装コンポーネント

| コンポーネント | 説明 |
|---------------|------|
| `PaymentService` | 仮払い・確定払い・返金のビジネスロジック |
| `StripeWebhookController` | Stripe Webhook受信 (payment_intent.succeeded, transfer.created 等) |
| `PaymentController` | 画家向け支払い画面 |
| `PayoutController` | モデル向け受取管理画面 |
| `StripeOnboardingController` | Connected Account 作成・本人確認フロー |

### 3.5 Webhook イベント

| イベント | 処理 |
|---------|------|
| `payment_intent.succeeded` | 仮払い成功 → payments.status = 'held' |
| `payment_intent.payment_failed` | 支払い失敗 → 画家に通知 |
| `transfer.created` | 確定払い完了 → payments.status = 'completed' |
| `charge.refunded` | 返金完了 → payments.status = 'refunded' |
| `account.updated` | Connected Account 状態変更 → stripe_accounts 更新 |

## 4. 画面設計

|------|------|

## 5. セキュリティ要件

| 項目 | 対策 |
|------|------|
| カード情報 | サーバー側では一切保持しない（Stripe Elements / Checkout Session を使用） |
| Webhook 検証 | Stripe 署名検証（`stripe-signature` ヘッダ）を必ず実施 |
| HTTPS | 決済画面は HTTPS 必須 |
| 二重支払い防止 | Idempotency Key を使用 |
| 不正取引検知 | Stripe Radar を有効化 |

---

## 6. 法的要件

| 項目 | 対応 |
|------|------|
| 資金決済法 | エスクロー方式の場合、資金移動業登録が必要か法務確認 |
| 特定商取引法 | プラットフォーム事業者としての表記義務 |
| 領収書発行 | 電子帳簿保存法に準拠した形式 |
| 消費税 | 手数料に対する消費税の扱い |
| インボイス制度 | 適格請求書発行事業者の登録要否 |
